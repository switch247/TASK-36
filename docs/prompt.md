Create a ProctorOps Exam Administration platform that runs entirely on an on-prem workstation or local LAN server to manage high-stakes test sessions from intake through printed outputs and post-session reporting. Administrators configure reusable form templates for registering candidates, proctors, rooms, and exam sessions, including required-field checks, data type and range rules (for example, room capacity must be 1–500, exam duration 15–360 minutes, and dates shown as MM/DD/YYYY with 12-hour times). Front-desk staff use a Dioxus-based web UI optimized for fast entry, supporting barcode/QR scan input for candidate IDs and booklet/asset tracking, plus attachment capture for supporting files (jpg/png/mp4/mp3/pdf/docx up to 25 MB each, maximum 10 files per record). The interface provides immediate validation feedback, duplicate warnings, and automatic structured metadata such as capture time, operator, device label, and file fingerprints. Coordinators generate exam outputs from templates, producing admit cards, seating charts, door signs, proctor packets, and summary reports with configurable sorting, pagination, and PDF/Excel/CSV export; printing must support a “test print” watermark and a final print mode that locks the template version used. Role-based access is enforced for Administrator, Exam Coordinator, Proctor, and Auditor, with menu visibility matching permissions. A local Operations & Reporting Center provides configurable dashboards for seat utilization, materials inventory, near-expiry items (for example, badges or supplies expiring within 30 days), incident/return rates, and multi-dimension filtering; notifications appear as in-app alerts and optional exportable message drafts for manual SMS/email use without any sending capability.

The backend uses Rocket to expose REST-style APIs consumed by the Dioxus frontend, keeping the UI and server decoupled while remaining fully functional offline. MySQL persists master records (candidates, staff, rooms, exams, assets) with extensible custom fields, versioned change history, and a guided merge flow when potential duplicates are detected using configurable thresholds (exact match on ID, or 90% similarity on name plus same date of birth). A built-in data cleansing pipeline standardizes units, USD currency formatting, and date-time normalization; it supports field mapping, missing-value defaults, deduplication, and outlier flags (for example, capacity deviations beyond 3× typical room size), and performs place-name standardization using a locally stored ZIP/city reference table rather than any online geocoding. Authentication is strictly local username/password; passwords must be at least 12 characters with complexity rules and are stored using BCrypt or SCrypt, with account lockout after 5 failed attempts for 15 minutes. The system supports both session-based auth (30-minute idle timeout) and JWT (8-hour expiration) while enforcing RBAC at the API level. Sensitive fields such as date of birth are encrypted at rest at the application layer, and views used for reporting mask identifiers by default, with all access and exports logged for audit.
